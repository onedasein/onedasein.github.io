## 事情的起因

下午想把 jyy 老师 GSE 课程第六讲的 [lecture notes](https://jyywiki.cn/GSE/2026/lect6.md) 存到本地，交给 agent 读。顺手在 Neovim 里 `Ctrl+Shift+V` 一贴——文本不是"啪"地出现，而是一行一行往下长。几千行的文档要等上好几秒，中间还能看到屏幕在滚。

`Ctrl+Shift+V` 明明是终端的快捷键，为什么会把 Vim 拖慢？顺着这条线查下去，发现问题的根源并非是Vim 性能不行,而是**终端粘贴和 Vim 自己的粘贴，走的并非同一条路**。

## `Ctrl+Shift+V` 的机制

在终端里按 `Ctrl+Shift+V`，是**终端**（我这里是 Alacritty）去 Wayland 剪贴板里取数据，然后写进 pty（伪终端）。Vim 从 pty 读到的只是字节流，它并不知道这是"粘贴"，只能按**用户键入**来处理。

Vim 自己的粘贴是另一回事：`p`、`P`、`"+p`、`:put +` 操作的是寄存器，本质是一次 `:put`，把整段文本直接放进 buffer。

所以"粘贴慢"这个说法其实不是问题的本质：慢的不是粘贴，是**文本被当成键入之后，Vim 逐字符处理的那一串开销**。

## 数据从剪贴板到 buffer 的五层开销

把数据从剪贴板走到 buffer 的整条路拆开，至少有这么几层：

1. **剪贴板传输**。Wayland 的剪贴板是 data offer，向数据所有者（浏览器、Electron 应用）现取。大段文本时，对方序列化 + 通过 socket 送过来本身就要时间，这期间 Vim 里什么都还没发生。
2. **pty 分块**。Linux 的 pty 输入缓冲只有几 KB，终端只能循环写、Vim 循环读，不存在"一次写进去"。
3. **Vim 的逐字符输入循环**。插入模式下每个字符都要过一遍映射展开、`InsertCharPre`、缩写、撤销同步；每个换行还要触发 `smartindent` / `indentexpr` / treesitter indent，再重绘屏幕。
4. **一次性的大事件**。就算文本整段进来，插入完成后仍会触发一次变更事件：treesitter 重新解析、gitsigns 重算 diff、nvim-cmp 处理超长行、indent-blankline 重画缩进线——这些都对字符数敏感。
5. **长行 + 折行**。粘贴一条超长单行（minified JSON、base64）时，`wrap` + `linebreak` 每次重绘都要重算断行位置，开销会随行长迅速放大。

## 为什么 GUI 应用粘贴不慢

同样的文本在浏览器、编辑器里用 `Ctrl+V` 贴，几乎瞬间完成。差别不在于"粘贴"这个动作，而在于数据被交给程序的方式。

GUI 应用是**自己去拿**数据的：通过窗口协议（X11 selection / Wayland data offer）向剪贴板所有者要整段文本，然后调用控件自己的插入接口，比如 GTK 的 `gtk_text_buffer_insert()`、Qt 的 `QTextCursor::insertText()`。对程序来说这是**一次插入**——改一次文档模型、标一次脏区、重绘一次，撤销也合并成一步。贴 1MB 和贴 10 个字的成本结构是一样的：一次操作加上一次重排。

终端里的 TUI（终端界面程序）做不到这一点。终端不知道 pty 里跑的是什么程序，也没法调用它的接口，唯一的选择是把剪贴板内容当作"用户以极快速度敲键盘"写进 pty。pty 缓冲只有几 KB，写满就得等 TUI 消费，所以粘贴速度实际上被 TUI 的处理速度卡住。而 TUI 收到的字节只能一个字符一个字符地走输入管线：模式分派、映射、`InsertCharPre`、撤销记录、缩进、重绘。屏幕上"一行行长出来"，就是这个逐字符处理队列的实时投影。

总结来说：**GUI 里粘贴是"把一段文本交给文档"，终端里粘贴是"模拟打字"**。前者的成本与字符数基本无关，后者的成本与字符数成正比。前面列的五层开销里，第 3、4、5 层在 GUI 里要么不存在，要么只发生一次。

GUI 也不是永远快，只是慢的地方不一样：浏览器 textarea 贴几 MB 要重新布局，富文本编辑器要一次性生成大量样式，Electron 应用要跨进程传剪贴板数据——但这些都属于"一次插入之后的处理"，而不是"每个字符都走一遍流程"。这正好是终端粘贴慢的镜像。

## 解决过程

## 解决方案

### 首选：用寄存器粘贴，别用终端粘贴

Neovim 配好 `clipboard=unnamedplus` 之后，普通模式直接 `p` 就是系统剪贴板；想稳妥一点用 `"+p`，或者按行整段插入：

```vim
" 普通模式
p
"+p
:put +
```

`p` 是一次 `:put` 操作，不经过插入模式，也不触发 `InsertCharPre` 这类逐字符回调，长文本基本是瞬时完成。经典 Vim 是 `-clipboard` 构建，但 `vimrc` 里装了 `jasonccox/vim-wayland-clipboard`，`"+p` 同样能用。

### 必须用 `Ctrl+Shift+V` 时：加一个粘贴模式开关

`set paste` 会临时关掉 `autoindent` / `smartindent` / `indentexpr` 和插入模式映射，`lazyredraw` 抑制中间重绘：

```lua
-- ~/.dotfiles/nvim/lua/config/keymaps.lua
vim.keymap.set("n", "<F2>", function()
  local on = not vim.o.paste
  vim.o.paste = on
  vim.o.lazyredraw = on
  -- 可选：粘贴期间让重活插件闭嘴（粘完恢复）
  vim.o.eventignore = on and "TextChangedI,CursorMovedI" or ""
  vim.notify("paste mode " .. (on and "ON" or "OFF"))
end, { desc = "Toggle paste mode" })
```

流程是 `F2` → `i` → `Ctrl+Shift+V` → `Esc` → `F2`。注意 `paste` 是全局选项，用完一定要关掉。

> 如果只是偶尔粘一次，`eventignore` 可以不加；它会让补全、gitsigns 这类依赖光标事件的插件在粘贴期间停止响应。
{: .prompt-tip }

### 超大文本：走命令和文件，不走键盘

```vim
:r !wl-paste -n          " 把剪贴板当文件读进来，一次 read 操作
:r /tmp/big.txt          " 或者先存成文件再读
```

`r !` 是同步执行外部命令再整块读入，几 MB 的文本也比终端粘贴稳定。

### 几个顺手的小开关

```vim
:set nowrap        " 粘超长单行时临时关折行
:set noundofile    " 一次性灌大文本，避免事后写超大 undo 文件
:Gitsigns detach   " 临时卸掉 diff 计算，粘完 attach 回来
```

## 总结

- **"终端粘贴"不等于"编辑器粘贴"**。快捷键归属谁，决定了数据走 pty 还是走寄存器，这是两条性能完全不同的路。
- **慢不一定是编辑器慢**。先分清是传输慢、输入慢，还是插入之后的事件慢，再决定优化哪一段。
- **能用一次性接口就不走逐字符路径**。`:put`、`:r !` 都是"整块"语义，天然比模拟键入快。
- **bracketed paste 解决的是正确性，不是性能**。它让粘贴不被当成命令、不触发自动缩进，但文本仍要过输入链路，长文本的插入后事件也照旧。
